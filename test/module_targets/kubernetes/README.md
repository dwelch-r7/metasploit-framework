# Kubernetes API and pod lab

~~~sh
bundle exec ruby tools/dev/run_module_target_tests.rb kubernetes
bundle exec ruby tools/dev/run_module_target_tests.rb kubernetes_exec
~~~

The official K3s v1.32.3+k3s1 image runs a real API server, scheduler, kubelet and
containerd. The configuration follows the upstream
[container Compose example](https://github.com/k3s-io/k3s/blob/v1.32.3%2Bk3s1/docker-compose.yml).
K3s and the official Python 3.11.11 Alpine pod image are pinned by image digest.
Internet registry access is needed to pull the pod image into nested containerd.
DNS, ingress, external load balancing, metrics and storage add-ons are disabled
to keep readiness and state bounded.

The K3s container is privileged, as required for its nested runtime. It uses a
private Docker bridge, PID/cgroup namespaces, tmpfs and four task-owned named
volumes. Only its API is published on a random loopback port. It mounts no host
files, Docker socket, host network or existing kubeconfig. This remains a
privileged container sharing the Docker engine's kernel and devices. A pod
created by the module mounts the K3s container's root filesystem at /host_mnt;
the native namespace/mount audit must demonstrate that this root belongs to the
task container.

Native kubectl and HTTPS controls validate exact server version, real RBAC,
successful/rejected authentication, pod/secret resources, projected service
account configuration, empty/missing resources, repeated exec with fresh file
proof and pod creation/deletion before module assertions. All tokens, keys,
certificates and secret passwords are generated public lab data. Native stdout,
stderr, statuses and API documents are retained alongside module output. A real
in-pod urllib request verifies the projected token, namespace, CA and service
environment against the internal HTTPS API before any module runs.

The enumeration profile covers every action, singular/name lookups, both output
formats, exact native secret bytes and five loot files per secret-collection
run, fallback namespaces,
and meaningful 401/403/404 and empty cases. Database credential/service/note
persistence is outside this profile. The execution profile additionally covers
the declared Meterpreter configuration/routing path through a genuine pod.

Per-case state assertions precede operator recovery. Arbitrary command proof
files are removed explicitly by the test operator. Module-created pods are
observed as retained, matching the module's documentation, then deleted by the
operator. The runner owns and removes the full cluster, nested pods, volumes and
network, including on failure. A repeat requires the expected pod/file state
to be restored. Secret collection repeats twice in each of JSON and table
formats. Operator pod deletion retains the native default grace period and
waits up to 40 seconds for its documented 30-second grace to finish.

This is one Linux amd64/Kubernetes release with default containerd networking.
Other Kubernetes releases/distributions, x86, Windows pods, external clusters,
alternate authentication/plugins and database persistence are not covered.
Registration alone does not imply qualification. Existing human module
Scenarios remain historical evidence and are not generated by these tests.
