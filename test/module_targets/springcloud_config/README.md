# Spring Cloud Config file-collection lab

Preparation and both affected/fixed release branches run serially:

```sh
DOCKER_CONTEXT=default BUILDX_BUILDER=default bundle exec ruby \
  test/module_targets/springcloud_config/run.rb
```

These profiles are under qualification. A fixture starting or an HTTP 200 does
not prove the module collected its requested file.

Six profiles exercise four original server/client library pairs (2.1.8, 2.1.9, 2.2.2 and 2.2.3) match
Maven Central. Immutable distribution layer and executable-archive SHA256 values
are in `vendor.json`. Preparation downloads and extracts only the pinned archive
onto the host, without importing target layers into Docker's backing filesystem.
The cached official Java 8 image runs Spring's own `ConfigServerApplication`
through its original Boot loader. No controller or vulnerability code is changed.
Source and build instructions are available through the pinned Spring tags and
[distribution repository](https://github.com/hyness/spring-cloud-config-server).
The distribution's unused JDBC/security backends are excluded through supported
Spring Boot configuration. Tests cover the native filesystem backend.

The exposed configuration uses the vendor regression's relative `file:./` search
location. Ordinary configuration and resource routes must work. An independent
client must then read exact outside-file bytes on affected releases and receive
404 on fixed releases. The [vendor fix](https://github.com/spring-cloud/spring-cloud-config/compare/v2.1.8.RELEASE...v2.1.9.RELEASE)
adds a resolved-resource location check. An absolute search location does not
reproduce this particular control and is retained separately in setup evidence.
The image tagged 2.1.6 actually contained library 2.2.1; it is not counted as 2.1
coverage.

The fixed releases refuse even ordinary resource files under the relative
location used by the vendor regression, while their configuration endpoint
works. Those preflight failures are retained without a module verdict. Healthy
fixed profiles use an absolute location; separate absolute-location profiles
on both affected releases establish that this configuration also refuses the
traversal. Every current profile must serve an ordinary resource before testing
collection. Root-level files use an explicit repository label because the
default-label shortcut overlaps the environment route.

Each functional profile runs two containers, capped at 1,024 MiB, 1.8 CPUs and
384 tasks. Only target HTTP is published on loopback. Sources, original archives
and proof files are read-only; target temporary storage is capped at 128 MiB.
No persistent Docker volume or additional database is needed. The wrapper
prepares immutable archives before using the shared guarded acceptance launcher.

Public module runs collect root-level, ordinary, Unicode/space-named, binary and empty files,
and refuse missing files. Each runs twice. Exact loot bytes establish success;
ordinary configuration JSON or an error page cannot qualify collection. All 256
binary octets are generated by the preparation source rather than stored as an
opaque binary. A tracked empty placeholder provides the mount point inside
the read-only proof directory. Native controls run before and after, and OOM/PID counters, target
process identity and empty session/job registries are checked.

Other repository providers, authentication modes and proxy/context prefixes
are outside these initial profiles. Existing human module Scenarios are retained.
