# Ollama registry traversal and command execution

```sh
MODULE_TARGET_NAMESPACE=ollama-local bundle exec ruby tools/dev/run_guarded_module_target_tests.rb ollama_rce ollama_rce_fixed
```

Run serially. Each profile builds from an official pinned Linux amd64 image:
Ollama 0.1.33 or 0.1.34, Ubuntu 22.04.4, UID 0. `vendor.json` records the image
and observed Ollama/libc/dynamic-loader hashes. Adding the resident Python
observer must leave all three vendor files unchanged. The application is still
the original `/bin/ollama serve`; CPU/thread limits avoid loading GPU runners.
The native constructor is built from the included C source with GCC, independently
of the module's Metasm-generated library. No model weights are downloaded.

The native gate first loads the harmless library through ordinary `LD_PRELOAD`
and `/usr/bin/true`. A normal OCI pull registers a minimal GGUF model and the
real API reports its family. Traversal must then write exact quote, backslash,
Unicode and CRLF bytes on 0.1.33. The library/preload chain must produce a proof
whose executable is the genuine CPU runner, parent PID is the existing Ollama
server and UID is zero. A chat error or timeout alone proves nothing. On 0.1.34,
the positive controls must still pass before digest-format rejection and absence
of the traversal file are accepted. This follows the
[vendor advisory](https://github.com/advisories/GHSA-8hqg-whrw-pv92) and
[original research](https://www.wiz.io/blog/probllama-ollama-vulnerability-cve-2024-37032).

**Never exec helpers or enable a Docker healthcheck while `/etc/ld.so.preload`
is armed.** A dynamic helper could consume the preload and create a false proof.
The resident observer starts before arming. Readiness, physical evidence, process
state, cgroup events and exact fixture recovery use host HTTP and Python file
APIs. The observer is an unauthenticated lab fixture; both ports publish only on
loopback. Its file API is restricted to the task directory, proof and preload.

After calibration the actual console module must return reason-bearing
Appears/Safe. The vulnerable profile executes `linux/x64/exec` twice on the same
selected object, without changing the default target or traversal depth. Passive
traces retain original requests/responses, generated library bytes and the
physical preload immediately before the module's own chat trigger. The target
library must equal those generated bytes and each command must write its exact
UID-zero proof. Model aliases, framework jobs and sessions must be absent.
The fixed profile repeats AutoCheck refusal and verifies no delivery method runs.

Command payloads explicitly use `AllowNoCleanup=true`: there is no session to
provide FileDropper's file API. The remaining library is recorded before resident
fixture recovery. These tests do not qualify automatic library cleanup, default
Meterpreter sessions, alternate payload families, other releases or nonroot
deployments. Automated captures do not replace human module Scenarios.

Each stack uses one container capped at 1 CPU, 1024 MiB memory/equal swap and
128 PIDs. The guarded runner uses a unique project, task labels and a shared lock,
then removes finished/failed stacks and ephemeral resources. The native registry
server closes in `finally`. Follow the repository lifecycle rule in
[CAMPAIGN.md](../CAMPAIGN.md); retain exact resource IDs and verify absence.
